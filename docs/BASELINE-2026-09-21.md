### Login, durable membership and legacy assurance

`app/api/auth/route.ts` lowercases the supplied email, looks up an active approved `members` row and verifies a member-selected scrypt password. Hash parameters are N=16384, r=8, p=5, with 15–128-character policy and local common-password screening. `issueSession` atomically checks current credential hash and active member before issuing a random 256-bit token, stored as a hash.

`sessionUser` joins `auth_sessions.member_id` to `members.id` and `auth_credentials`. It emits both `memberId` and a legacy `userId`. `lib/pilot/service.ts:identity` currently resolves `user_id`, then falls back to lowercased email when `user_id` is null and writes the association. That compatibility path operates on trusted existing session data today; it is not proof of an existing OIDC takeover. It must not become the association rule for new external providers. Member CRUD, owner lookup, Access email matching and email-change workflow are additional email-sensitive touchpoints.

The administrator approves a member and privately issues a 96-bit, hashed setup code, valid seven days, for a member without a password. Recovery uses a 128-bit, hashed code valid one hour; issuing it requires administrator `identityVerified: true` attestation. Consumption and password replacement use guarded database batches and clear old sessions/setup/recovery records. These are existing password-enrollment/recovery ceremonies, not federated invitations or proof that delivery was trustworthy. E-05 must supply the human verification/custody process.

The cookie is `__Host-supply-session; Secure; HttpOnly; SameSite=Lax; Path=/` with no Domain. Member idle/absolute limits are **7/30 days**; admin **30 minutes/12 hours**. Renewal changes expiry at most once per five minutes and preserves original absolute deadline. Current-session logout, administrative session revocation and password-change revocation of other sessions exist. Ordinary member sign-out-all, method provenance, security epoch and action-bound fresh-proof grants do not.

Deactivation, role and shop-permission changes delete sessions and current member state is checked in mutation transactions. Deactivation does not invalidate all pending setup/recovery codes; reactivation within a code's validity can make it usable again. Revoke-all currently means sessions, not credentials or pending enrollment authority. New containment needs explicit semantics and a durable epoch.

### Administrative Access and capabilities

The live Access application selects Google and an explicit-email allow policy, with 30-minute duration. Independent MFA is configured for security keys/biometrics at that policy; organization MFA also allows TOTP. An OTP IdP exists in the account but is not selected for this admin app. No actual sign-in/MFA/no-MFA denial was performed. Do not equate a successful Access redirect or fresh JWT `iat` with a tested fresh factor challenge; [Cloudflare's session documentation](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/session-management/) describes separate session lifetimes.

`lib/security/admin-access.ts` uses maintained JOSE/JWKS verification with RS256, exact configured issuer/audience and required `exp/iat/sub/email`. Email must match the already-authenticated admin; proof expires within token and 30-minute bounds. The Access subject is stored against that app session, not pre-provisioned as a durable `(issuer, subject) → member/capability` identity. Current roles are member/admin plus owner-by-configured-email, with owner-only administrator grants/management. Any commerce administrator can support ordinary members. The D-06 capability split and D-09 fresh action proof are absent.

Current exact-Origin checks and host-only cookies are useful existing protections. They do not demonstrate the entire future separate-host protocol, which also needs CSRF tokens, browser/verifier binding, fixed callback/audience/purpose and replay-safe final consumption. No member OIDC client, WebAuthn verifier, provider-subject registry, bootstrap grant, handoff or roster importer was found.

## Data integrity and recovery

`members.id` is the durable business identity. Orders, payments, balance ledger, rewards, profiles, raffle entries and other activity reference it. Member IDs must survive migration unchanged; provider email/name changes must update metadata without moving ownership. Email remains unique in the old model; automatic normalization/merging of historical members is unsafe. Lost original email capitalization cannot be reconstructed from a lowercased stored value.

Financial writes use integer amounts, guarded D1 batches, current session/role/Access checks and idempotency fingerprints. Order-item price/cost/option/tax snapshots preserve purchase history. Corrections use compensating ledger/payment/inventory effects. Reward spendable balance is earned ledger minus redemptions; redemption must not reduce the historical-earned display. Credit issuance and later explicit application to tab/purchase are separate auditable effects. Profile defaults/opt-outs, season results and guest merchandise isolation are migration invariants. Fixture checks passed; no live balances, member grants, activity counts or reconciliation totals were inspected.

`initialize` in `lib/pilot/service.ts` may create settings/owner/seed data when settings are missing; `identity` may attach a legacy user ID during a read. An eventual identity-only lookup must not invoke implicit business initialization. Do not point previews or restored databases at production bindings.

Encrypted backup tooling and an isolated in-memory SQLite verifier exist. The verifier checks integrity, foreign keys and seven legacy table counts; it does not prove reconciliation of every modern ledger/reward/raffle/privacy table or restored revocations. Synthetic encryption tests passed. No production export, private R2 copy, Time Travel retention confirmation, named custodian, accepted RPO/RTO or protected restore drill was obtained. Code rollback cannot repair those gaps and may reintroduce older security behavior, as `SECURITY-IMPLEMENTATION.md` warns.

Scheduled security cleanup is bounded to 500 expired rows per table per run; successful-login cleanup separately uses unbounded deletes for expired limits/sessions. Neither is an accepted comprehensive retention policy. D-15 concerns new identity metadata, not deletion of financial history.
